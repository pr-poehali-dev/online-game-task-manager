# Заливка файлов в лаунчер (VPS) — рабочий журnal разработки

Служебный документ. Веду его сам на каждом этапе: что сделано, что решено,
что осталось выяснить, инструкции себе на будущее. Не для конечного
пользователя (тот получает только короткие резюме в чате) — здесь допустимо
максимально подробно, технически, без причёсывания.

**Каждый этап работы — отдельный коммит.** Перед тем как закончить этап,
обновляю этот файл (секция "Прогресс" внизу) — фиксирую, что сделано именно
в этом заходе.

---

## 1. Цель фичи

Пользователь администрирует несколько игровых серверов Lineage2 (проект на
poehali.dev — таск-менеджер команды, раздел «Патчи» уже хранит файлы
сервера в S3 + PostgreSQL, дерево папок в UI). Нужно добавить возможность
**заливать файлы прямо из дерева патчей на внешний VPS**, где стоит
Lineage2-лаунчер, который считывает список файлов из XML.

Текущий ручной процесс пользователя:
1. Обрабатывает файлы программой **UPMaker** (see `.tmp/upmaker/` — присланный
   .zip, распакован туда же) → на выходе получает `.zip`-обёртки над каждым
   файлом + `files.xml` с hash/size.
2. Вручную заливает архивы на VPS по FTP/SSH.
3. Вручную правит XML-файлы на VPS (добавляет/убирает записи).
4. Лаунчер клиента сам качает файлы, ориентируясь на XML.

Наша задача — автоматизировать шаги 2–3 (и по возможности шаг 1 — упаковку
в .zip с правильным форматом) прямо из дерева патчей в приложении: у файла
в дереве должны быть **две кнопки** — «Залить в быстрое обновление» и
«Залить в полное обновление».

## 2. Формат UPMaker (исследовано на присланном .zip)

Присланный `upmaker.zip` распакован в `.tmp/upmaker/upmaker/`:
```
upmaker/
  option.ini              — просто пути input/output самой EXE-программы, не нужен нам
  UPMaker.exe
  source/System/*.dat     — исходные несжатые файлы
  source/System_eng/*.dat
  patch/files.xml         — реестр (см. ниже)
  patch/System/*.dat.zip  — готовые к заливке архивы
  patch/System_eng/*.dat.zip
```

**`patch/files.xml`:**
```xml
<?xml version="1.0" encoding="utf-8"?>
<list>
<set file="\System\etcitemgrp.dat" hash="15a04d19fda53b1eb2cb2963c8adc5d0" size="76655" />
<set file="\System\itemname-e.dat" hash="a8b690618de6114bed0967134071911f" size="286640" />
...
</list>
```
- `file` — путь **с ведущим `\`**, разделитель `\` (Windows-style), от корня
  сервера (`\System\...`, `\textures\...` и т.д.)
- `hash` — MD5, но **не файла на диске**, а посчитан от **исходного (source)
  файла**, до упаковки в .zip. Проверено: `md5(source/System/etcitemgrp.dat)
  == 15a04d19fda53b1eb2cb2963c8adc5d0` — совпадает с `hash` в XML.
- `size` — размер **упакованного `.zip`**, НЕ исходного файла. Проверено:
  `76655` = размер `patch/System/etcitemgrp.dat.zip`, а не `source/...dat`
  (76464 байта). **Важно не перепутать при генерации.**

**Формат `.zip`-обёртки (исследовано через `python3 -c "import zipfile..."`):**
- Один файл внутри архива, имя = basename исходного файла (без пути)
- Обычный ZIP_DEFLATED, но UPMaker кладёт **ZIP64 extra field всегда**
  (даже для маленьких файлов) — это видно по `extra` полю central directory
  (`\x01\x00\x10\x00...` — ZIP64 extra tag `0x0001`). Обычный `zipfile.ZipFile`
  в Python по умолчанию **не** добавляет ZIP64 extra для маленьких файлов —
  создаёт чуть другой (но валидный) zip. **Нужно перепроверить, критично ли
  это для лаунчера** — скорее всего нет (большинство ZIP-ридеров ZIP64
  extra игнорируют, если размеры укладываются в 32 бита), но стоит
  протестировать реальной заливкой на тестовую директорию, прежде чем
  полагаться.
- local file header у UPMaker: `compression method = 8 (deflate)`,
  версия `45` (0x2D) — это как раз версия, требуемая для ZIP64.
- CRC совпадает с обычным zlib.crc32 контента.
- **Вывод:** для генерации архива на бэкенде можно использовать
  Python `zipfile.ZipFile(..., zipfile.ZIP_DEFLATED)` — содержимое читается
  тем же движком, что и обычный zip. Financial risk низкий, но пункт из
  плана тестирования: залить тестовый файл в тестовую директорию на
  forge.la2era.com и проверить, что лаунчер (или хотя бы `unzip`/7-Zip на
  Windows) корректно открывает.

## 3. Структура VPS (реальная, со скриншотов пользователя)

**Директория Б (судя по размеру файлов явно меньше — вероятно "быстрое

**Обновление — получен реальный `files.xml` с VPS пользователя**
(`test_updater/C4/files.xml`, ПОЛНОЕ обновление — сохранён в
`.tmp/vps_screens/files_full.xml`, 450 записей `<set>`). Отличия от
формата UPMaker:
- Имена папок в пути — **строчными буквами**: `\system\`, `\system_eng\`,
  а не `\System\`, `\System_eng\` как в UPMaker. Вывод: при генерации пути
  для XML **надо lower-case** сегменты пути (или хотя бы не полагаться на
  регистр из дерева патчей — привести к нижнему регистру явно).
- В списке присутствуют ВСЕ типы файлов, не только `.dat`: `.dll`, `.ukx`
  (анимации/модели), `.utx` (текстуры) — подтверждает ответ пользователя
  «все файлы в .zip как в UPMaker».
- Формат тега идентичен UPMaker: `<set file="\...\name.ext" hash="MD5"
  size="N" />`, корень `<list>...</list>`, XML-декларация `utf-8` с BOM
  (`\ufeff` в начале файла — сохранён в исходнике, нужно воспроизводить и
  при генерации, чтобы не отличаться от привычного пользователю формата).
- Обнаружена доп. папка в путях, которой не было в скриншотах: `\profII\`
  — значит список folders не ограничен тем, что видно на скриншотах папок
  верхнего уровня (или это подпапка внутри одной из видимых). Не критично
  для реализации (мы всё равно берём путь из дерева патчей как есть).
- **Не удалось подтвердить** совпадает ли `size` с размером `.zip`-обёртки
  или с размером исходного файла — у меня нет доступа к реальным файлам
  этого сервера (только список путей/хэшей/размеров из XML), не могу
  сравнить. UPMaker-пример показал `size` = размер `.zip`. Раз формат тега
  идентичен и заявлено, что процесс через тот же UPMaker — считаю рабочей
  гипотезой, что `size` тоже размер `.zip`, но **это надо перепроверить
  на первом тестовом файле** (залить, сравнить `ls -la` реального .zip на
  VPS с числом в XML).
- `files_ftp.xml` пока не прислан отдельно — пользователь сказал прислать
  позже. Есть вероятность что `files.xml` и `files_ftp.xml` идентичны по
  формату, но собраны для разных путей раздачи (сам файл на HTTP/веб vs
  FTP) — уточнить при получении.

**Пути на VPS (ответ пользователя):**
- Полное обновление: `forge.la2era.com/test_updater/C4` — это ВЕБ-путь
  (URL), не обязательно совпадает с абсолютным путём на файловой системе
  сервера (например `/var/www/forge.la2era.com/test_updater/C4` или
  похоже, зависит от конфига Nginx/root). **Нужно уточнить абсолютный
  файловый путь для SFTP** — веб-адрес пользователь дал для ориентира по
  структуре, но SFTP пишет напрямую в файловую систему, не через HTTP.
- Быстрое обновление: `forge.la2era.com/test_updater/C4/Patch` — то есть
  быстрое обновление физически ВЛОЖЕНО в полное (подпапка `Patch/` внутри
  директории полного обновления), а не отдельная параллельная директория,
  как я предполагал раньше по скриншотам. Это важно для UI (обе кнопки
  могут указывать на пути, где одна — подпуть другой) и для XML-логики —
  возможно `files.xml` (полное) содержит вообще все файлы сервера, а
  `Patch/files.xml` (быстрое) — только последний патч/дельту. Нужно будет
  прояснить на практике при первой тестовой заливке.
- Пользователь явно попросил: раз оба `files.xml` называются одинаково, но
  лежат по разным путям и выполняют разные задачи — **у себя в коде/БД
  подписывать их по-разному** (не `files.xml`/`files.xml`, а например
  `fast_xml_path` и `full_xml_path`, или `xmlFileName` per-context) — уже
  так и планировалось (4 отдельных поля per server: fast xml url, full xml
  url, fast dir, full dir — см. CabinetServers.tsx заготовку).

## 4. Текущая архитектура проекта (что уже есть, на что опираемся)

### 4.1 Раздел «Патчи» (`src/pages/index/Patches.tsx` + `PatchesTreeFolder.tsx`)
- Дерево файлов сервера строится из `patch_files` (БД) + S3 (реальные байты)
- У каждого файла в дереве уже есть инлайн-кнопки: Download, редактировать
  DDF (для .dat), прикрепить к задаче (Paperclip), удалить (Trash) —
  см. `PatchesTreeFolder.tsx` (кнопки в файле, строки ~196–266 на момент
  этого журнала)
- Загрузка файла в патчи — чанками (`file_init` → `file_chunk` →
  `file_complete`), реализовано в `backend/patches/index.py` +
  `src/pages/index/patchesApi.ts` (`uploadFileInChunks`, CHUNK_SIZE=1.5МБ)
- Прогресс загрузки уже показывается в UI (progress bar + "Файл X/Y · Z%",
  см. `Patches.tsx`)
- **План:** по аналогии с этими двумя (Download/Trash) кнопками добавить ещё
  ДВЕ: «Залить в быстрое обновление» и «Залить в полное обновление» — по
  клику бэкенд берёт уже загруженный в S3 файл патчей, упаковывает в .zip
  (формат UPMaker, см. раздел 2), заливает на VPS по SFTP в нужную папку,

### 4.2 Таблица `servers` (БД)
Текущие колонки: `id, label, color, sort_order, protocol, description,
created_at` (см. `db_migrations/V0026...sql`, `V0063...sql`).
**Нет пока места для**: SSH-хост/логин/пароль, путей fast/full директорий на
VPS, путей/имён XML-файлов. Это будет новая миграция (добавить колонки к
`servers`, т.к. пользователь подтвердил — один VPS, но у каждого сервера
своя папка → SSH-реквизиты общие один раз, но пути — per-server).

**Вопрос на будущее:** хранить SSH-креды (host, login, password) — на
уровне ОДНОЙ общей записи (раз VPS один на все сервера) или всё равно
дублировать в каждой строке `servers`? Пользователь сказал «один VPS, у
каждого сервера своя папка» → логичнее: SSH host/login/password — один раз
(например в новой таблице `launcher_config` или в секретах проекта), а
per-server — только 4 пути (fast xml, full xml, fast dir, full dir). Это
совпадает с уже существующей заглушкой в `CabinetServers.tsx`
(«Настройки лаунчера»: xml путь fast, xml путь full, папка fast, папка

### 4.3 Кабинет — `CabinetServers.tsx`
Уже есть визуальная заглушка (opacity-60, "скоро") с ровно теми 4 полями,
которые нужны:

- Адрес xml файла полной загрузки

- Адрес папки с файлами полной загрузки

Значит поля для путей на сервере пользователь уже предвидел заранее — не
нужно их придумывать, просто наполнить реальной логикой + добавить общие
SSH-реквизиты VPS (либо туда же, либо в раздел «Хранилище» по аналогии со
storage-config, см. `backend/storage-config/`, `CabinetStorage.tsx` — уже
есть похожий паттерн: раздел кабинета, доступный только владельцу, хранящий
чувствительные данные).

### 4.4 Похожий недавний прецедент: `backend/storage-config`
Только что реализовывали похожую фичу (S3/MinIO настройки через кабинет).
Важный урок оттуда: **облачные функции этого проекта не могут выполнять
`subprocess`/`os.system`** — деплой падает с "Potentially dangerous code
found: subprocess". Значит для SSH/SFTP нужна **чистая Python-библиотека**
(например `paramiko`), а не вызов внешнего `scp`/`ssh` бинаря через
subprocess. `paramiko` пока не установлен ни в одном `requirements.txt`
backend-функций (проверено `grep -rn "paramiko\|sftp\|ssh" backend/` — пусто).
**Нужно будет добавить `paramiko` в requirements.txt новой функции и
проверить, что sync_backend разрешает эту библиотеку** (некоторые чистые
Python C-extension зависимости, например `gmpy2`, уже используются в
`backend/patches` — значит компилируемые зависимости в принципе разрешены,
но не факт что именно paramiko пройдёт валидацию — нужно проверить на
практике при первом деплое).

## 5. Решения пользователя (зафиксировано по обоим раундам вопросов)

1. **Доступ к VPS:** SSH по логину и паролю (не по ключу).
2. **Топология:** один VPS, у каждого игрового сервера — своя отдельная
   папка на этом VPS (значит SSH-креды общие, пути — per-server).
3. **Формат архива:** ВСЕ файлы (не только .dat) заливаются в .zip-обёртке,
   как делает UPMaker — один файл на один .zip, тот же формат для текстур,
   моделей, звуков и т.д.
4. Тестовый прогон — пользователь создала тестовые директории:
   - Полное обновление (веб-путь): `forge.la2era.com/test_updater/C4`
   - Быстрое обновление (веб-путь): `forge.la2era.com/test_updater/C4/Patch`
     — ВЛОЖЕНО в полное, не параллельная директория
5. **SSH пользователь:** создаст отдельного пользователя сама (не root) —
   ждём хост/порт/логин, пароль придёт через `put_secret`.
6. **Статус заливки в UI:** да, показывать бейджи «fast/full» у файла в
   дереве патчей (аналог существующего бейджа "требуется залить в
   лаунчер" у задач, но это отдельная независимая логика/хранилище).
7. Реальный `files.xml` (полного обновления) получен и разобран — см.
   раздел 3 выше. `files_ftp.xml` — придёт отдельно.

## 7. Инструкции самому себе

- НЕ путать `launcher_uploaded`/`launcher_notify` (существующий функционал —
  просто бейдж-напоминание в задачах «требуется залить в лаунчер», не
  связан с этой фичей) с новой SFTP-заливкой — разные вещи, разный код.
- При генерации .zip — **hash в XML считается от исходного файла, size — от
  .zip-архива**. Не перепутать порядок при генерации записи.
- Путь в XML — с ведущим `\` и обратными слешами (Windows-style), даже если
  бэкенд на Linux — сохранять именно такой формат строки.
- Проверить лимит `MAX_FILE_SIZE` (200 МБ, `backend/patches/index.py`) —
  актуален ли для SFTP-заливки, или там свой лимит (SSH-таймаут функции

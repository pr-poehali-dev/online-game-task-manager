# Стримерская программа — план разработки

Рабочий документ для контекста. Статус: **этапы 0 и 1 выполнены, дальше этап 2 (сборщик)**. Обновлять по ходу работы (раздел «Журнал решений» внизу).

## 1. Цель

Прозрачный инструмент для сотрудников: мониторинг стримов игроков проекта на Kick, чтобы на основе их активности считать бонусы.

Сотрудник вставляет ссылку на канал Kick, дальше данные собираются автоматически. Данные можно сортировать и фильтровать.

### Что собираем (требование заказчика)

- стример запустил трансляцию (время старта)
- ник стримера на платформе
- название трансляции
- проверка наличия обязательных слов (по умолчанию «Aurora») в названии и тегах
- длительность трансляции
- количество зрителей
- стример завершил трансляцию

### Решения, принятые с заказчиком

| Вопрос | Решение |
|---|---|
| Масштаб | 10–50 стримеров |
| Точность | до минуты |
| Бонусы | пока только считаются, автоначисление в игре позже |
| Теги/слова | задаются сотрудниками для каждого стримера |
| Подключение стримера | старт: пассивный сбор по ссылке. OAuth-подтверждение владения — позже |
| Платформа | пока только Kick, но поле `platform` закладываем сразу |

### Открытый вопрос

Сколько хранить историю (сезон или больше года)? Влияет на архивацию снапшотов. До ответа считаем, что храним всё.

## 2. Главный риск и этап 0 (PoC)

Источник данных Kick не проверен. Из публичной документации известно (**не проверено на практике**):

- OAuth 2.1 с PKCE, есть токен уровня приложения (без участия стримера)
- есть методы получения данных о трансляциях, в списке трансляций есть поле `custom_tags`
- есть вебхуки смены метаданных, но подписка на чужой канал, скорее всего, требует разрешения стримера

Неизвестно, и это нужно выяснить до начала разработки:

1. Отдаёт ли токен приложения: статус эфира, название, теги, число зрителей, время старта.
2. Можно ли запросить сразу несколько каналов одним вызовом (критично для лимита времени облачной функции).
3. Лимиты запросов.
4. Не блокирует ли Kick запросы с нашего сервера (Cloudflare и т.п.).
5. Как по ссылке `kick.com/<slug>` получить канал, ник и аватар.

**Результат PoC:** короткий отчёт в разделе «Журнал решений» с выбранным источником данных. Если токен приложения не отдаёт зрителей или названия, пересматриваем архитектуру (запасной вариант: опрос публичных эндпоинтов, с оговоркой о хрупкости).

**Что понадобится от заказчика:** зарегистрировать приложение на Kick и добавить секреты `KICK_CLIENT_ID`, `KICK_CLIENT_SECRET` (через put_secret).

## 3. Архитектура

```
Внешний cron (раз в минуту, как у deadline-reminders)
        │  X-Cron-Secret
        ▼
backend/streamers-collector  ──►  Kick API
        │
        ▼
PostgreSQL: стримеры, сессии, снапшоты, события
        ▲
        │
backend/streamers (API панели)  ◄──  Фронтенд: раздел «Стримеры»
```

Принципы:

1. **Храним сырые данные, бонусы считаем на лету.** Правила бонусов будут меняться, поэтому хранится минутный снапшот (статус, название, теги, зрители, совпало ли условие). Любую новую формулу можно применить к старым данным.
2. **Сессия закрывается после 3 подряд проверок «не в эфире»**, чтобы обрыв связи не рвал эфир на две части. Время окончания ставится по последнему подтверждённому снапшоту.
3. **Индикатор здоровья сборщика.** Тихая остановка сборщика выглядит как «никто не стримит», поэтому на панели виден «последний успешный опрос», а при простое больше 5 минут уходит уведомление в Telegram.
4. **Идемпотентность.** Повторный запуск сборщика в ту же минуту не создаёт дублей (уникальный ключ `streamer_id + минута`).

### Ограничения платформы, которые нужно учесть

- Облачная функция по умолчанию живёт 5 секунд. 50 каналов нужно опрашивать параллельно или одним пакетным запросом, иначе не уложимся. Если не хватит, попросить заказчика поднять таймаут функции (Ядро → Функции → Настройки).
- Cron в проекте внешний (см. `backend/deadline-reminders`, секрет `CRON_SECRET`). Нужен ещё один внешний триггер раз в минуту. **Нужно, чтобы заказчик настроил его у себя.**
- Проект работает на self-hosted сервере заказчика. Все правила из `update/NOTES_FOR_ME.md` применяются к новым функциям (см. раздел 8).

## 5. Backend

### 5.1 `backend/streamers/` (API панели)
Python, `psycopg2`, схема токена как в остальных функциях (`X-Auth-Token`).

| action | Что делает | Права |
|---|---|---|
| `list` | список стримеров со статусом «в эфире сейчас» | просмотр |
| `add` | по ссылке: разбор slug, проверка существования канала в Kick, подтягивание ника и аватара | редактирование |
| `update` | пауза, заметка, привязка игрового аккаунта | редактирование |
| `delete` | удаление (или архив) | редактирование |
| `rules_get` / `rules_set` | правила по умолчанию и по стримеру | редактирование |
| `sessions` | история сессий: фильтры по датам, стримеру, совпадению правила, сортировка, пагинация | просмотр |
| `session_get` | сессия + снапшоты (для графика) + события | просмотр |
| `session_review` | подтвердить или оспорить сессию | редактирование |
| `summary` | сводка за период по каждому стримеру: часы, средний онлайн, доля эфира с правилом | просмотр |
| `export` | выгрузка в CSV | просмотр |
| `health` | состояние сборщика | просмотр |

Новые права (добавлять синхронно в `ALL_PERMISSIONS` в `backend/auth`, `backend/admin`, `backend/tasks`, `backend/ideas` и в `adminShared.ts`, `auth.tsx`):
- `streamers_view`
- `streamers_edit`

### 5.2 `backend/streamers-collector/` (сборщик)
Вызывается внешним cron раз в минуту, защищён `X-Cron-Secret` (как `deadline-reminders`).

Алгоритм одного запуска:
1. Получить токен приложения Kick (кэшировать на время жизни, не запрашивать каждую минуту).
2. Загрузить активных стримеров и их правила.
3. Опросить статус каналов параллельно (или пакетом, по результатам PoC).
4. Для каждого стримера сравнить с открытой сессией:
   - был офлайн, стал онлайн → открыть сессию, событие `stream_started`
   - онлайн → записать снапшот, посчитать `rule_matched`, при смене названия событие `title_changed`, при смене совпадения `rule_gained` / `rule_lost`, обновить пик зрителей
   - онлайн → офлайн: считать пропуски, после 3-го закрыть сессию, событие `stream_ended`
5. Обновить `streamer_collector_state`.
6. При ошибке Kick: записать `collector_error`, не закрывать сессии (иначе сбой API превратится в «все закончили эфир»).

Проверка правила: приведение к нижнему регистру, учёт `#` и пробелов, режим `any`/`all`, поиск в названии и/или тегах.

### 5.3 Уведомления
Использовать существующий механизм (`notifications` + Telegram, паттерн `_add_notif`/`_tg_send` из `deadline-reminders`).
- Сборщик не отвечает дольше 5 минут → сотрудникам с `streamers_edit`.
- (Версия 2) Стример вышел в эфир без нужного слова.

## 6. Frontend

Новый раздел «Стримеры» в боковом меню `ViewId` (`src/pages/index/`), по образцу «Патчноуты»/«Идеи». Файлы разбиваем на небольшие компоненты.

### Экраны
1. **Сейчас в эфире.** Карточки онлайн-стримеров: ник, название, зрители, таймер эфира, бейдж «условие выполнено / нет». Автообновление раз в 30–60 секунд.
2. **История сессий.** Таблица: стример, начало, конец, длительность, пик и средний онлайн, доля эфира с условием, статус проверки. Фильтры: период, стример, условие, статус. Сортировка по любой колонке. Экспорт в CSV.
3. **Карточка стримера.** Вкладки: сводка за период, график зрителей по сессии, лента событий, правила.
4. **Управление списком.** Добавление по ссылке, пауза, заметка, привязка игрового аккаунта.
5. **Настройки правил.** Правило по умолчанию и переопределение для стримера.
6. **Индикатор здоровья** сборщика в шапке раздела («последний опрос 40 секунд назад»).

## 7. Этапы и порядок работ

### Этап 0. PoC Kick API (≈1 день)
- Заказчик регистрирует приложение на Kick, добавляет секреты.
- Отдельный временный скрипт проверяет пять вопросов из раздела 2.
- Результат записывается в «Журнал решений». Решение «идём / меняем источник».

### Этап 1. Фундамент
- Миграции: `streamers`, `streamer_rules`, `stream_sessions`, `stream_snapshots`, `stream_events`, `streamer_collector_state`.
- Права `streamers_view` / `streamers_edit` во всех копиях `ALL_PERMISSIONS`.
- `backend/streamers`: `list`, `add`, `update`, `delete`, `rules_get/set`, `health`.

### Этап 2. Сборщик
- `backend/streamers-collector` с логикой сессий и снапшотов.
- Тесты логики на разборе сессий (старт, обрыв на 1–2 минуты, настоящий конец, смена названия).
- Заказчик настраивает внешний cron раз в минуту.

### Этап 3. MVP-панель
- Раздел «Стримеры»: «Сейчас в эфире», добавление по ссылке, история сессий с фильтрами и сортировкой, правила.
- Экспорт CSV.

### Этап 4. Аналитика и прозрачность
- Карточка стримера с графиком, сводка за период, лента событий.
- Проверка сессий (подтвердить/оспорить).
- Уведомления в Telegram о сбоях сборщика.

### Этап 5. Бонусы (отдельное обсуждение с заказчиком)
- Настраиваемые правила расчёта (за час эфира с условием, за средний онлайн, уровни).
- Отчёт за период для начисления вручную.
- Антифрод: флаг скачков зрителей.

### Этап 6. Подтверждение владения (OAuth)
- Кнопка «Подключить через Kick» для стримера, заполнение `ownership_verified`.
- Опционально: вебхуки вместо опроса для подключённых каналов.
- Опционально: личный кабинет стримера (только просмотр).

## 10. Журнал решений

- (дата) Создан план. Масштаб 10–50 стримеров, точность до минуты, бонусы пока только считаются, старт с пассивного сбора, теги задают сотрудники.
- **2026-10-05. Этап 0 (PoC Kick API) выполнен.** Секреты `KICK_CLIENT_ID`, `KICK_CLIENT_SECRET` заданы. Пробная функция `backend/kick-probe` удалена после проверки.

### Результаты PoC

**Работает (проверено на живых каналах):**
- Токен приложения: `POST https://id.kick.com/oauth/token`, `grant_type=client_credentials`, форма `application/x-www-form-urlencoded`. Ответ 200, `expires_in` = 5 184 000 с (60 суток). Токен кэшировать, не запрашивать каждую минуту.
- Данные канала без участия стримера: `GET https://api.kick.com/public/v1/channels?slug=a&slug=b...` (Bearer). Отдаёт `stream.is_live`, `stream.start_time`, `stream.viewer_count`, `stream.language`, `stream_title`, `category`, `broadcaster_user_id`.
- Список эфиров: `GET https://api.kick.com/public/v1/livestreams?broadcaster_user_id=...` (повтор параметра). Отдаёт `viewer_count`, `started_at`, `stream_title`, `category`, `profile_picture`. В выдаче только каналы, которые в эфире сейчас.
- **Пакетный запрос работает:** 10 слагов одним вызовом. Несуществующий канал просто отсутствует в ответе, ошибки нет.
- Вывод: стримеров подключать не нужно. Пассивный сбор по ссылке технически возможен, все требуемые поля (статус, ник/slug, название, старт, зрители, конец по пропаже) доступны.

**Не подтвердилось:**
- **Теги (`custom_tags`) не пришли** ни в `channels`, ни в `livestreams` при токене приложения. Возможно, поле появляется только у определённых каналов или требует иного права. Пока правила проверки слов считаем **по названию трансляции и категории**. Теги оставить как необязательное расширение (перепроверить на канале, где теги точно заданы).
- Заголовков с лимитами запросов (`RateLimit`) в ответах нет, лимиты неизвестны.

**Проблемы и риски:**
- **Нестабильность ответа.** Из 10 запрошенных каналов (все в эфире) вернулось 7: `dimasheff2`, `escsb` и несуществующий не пришли. Часть слагов, возможно, названа неверно (проверить написание), но надёжно это не установлено. Ответ на один и тот же запрос различался между вызовами.
- **Зависания.** 1 запрос из ~10 получения токена не вернулся за 3.5 с (облачная функция, лимит 5 с). Первые версии пробной функции упирались в таймаут 504.
- Вывод для сборщика: не считать «нет в ответе» за конец эфира. Это уже заложено в правило «3 подряд пропуска», нужны ещё повтор запроса при сбое, кэш токена и мягкая обработка таймаутов.

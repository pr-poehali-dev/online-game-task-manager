# Раздел "Логи" — заметки для восстановления контекста

ВНИМАНИЕ: этот файл (и весь backend/logs/) уже ОДИН РАЗ терялся между сессиями из-за бага в
.gitignore (правило `logs` без ведущего слэша случайно игнорировало папку backend/logs/) — баг
исправлен. Но кроме этого замечено, что часть точечных фиксов кода (не файлов целиком, а именно
конкретных изменений внутри `index.py`, сделанных в конце одной из сессий) периодически не попадала
в следующую сессию — причина не выяснена (возможно, коммит не успевал зафиксироваться до окончания
сессии). Из-за этого некоторые доработки (см. чек-лист) приходилось делать ПОВТОРНО. Держи этот
файл МАКСИМАЛЬНО подробным и актуальным после каждого значимого изменения — это единственная
защита от повторной потери контекста.

## Цель задачи
Раздел кабинета **"Логи"** (наравне с "Патчи"/"Патчноуты"): пользователь выбирает сервер (тот же
список, что в "Патчах" — таблица `servers`), выбирает вид лога (`cached`/`server`/`npc`), видит
разобранную таблицу событий с человекочитаемыми именами вместо числовых id (item_id → предмет,
npc_id → нпс, skill_id → скилл, action_id → действие). Прообраз — desktop-парсер пользователя
"LogParser AdvExt" (Actor Name/Account/IP, Item ItemID/ItemDB/Enchant, Action, диапазон дат, Nums
1-5 как доп.фильтры числовых полей, экспорт результата в HTML), переписывается на Python внутри
веб-приложения.

## Формат файлов лога (подтверждено на реальных образцах)
Имя: `{ГГГГ-ММ-ДД}-{HHMM}-{NN}-{тип}-in{0|1}.log`, например `2026-08-07-10020-01-server-in0.log`.
Файлы нарезаны примерно каждые 30 минут. Кодировка **cp1251** (не utf-8!). CSV без экранирования,
разделитель `,`, конец строки `\r\n`, **ровно 27 полей** во всех трёх типах логов.

**Уточнение пользователя (дословно, важно)**: "у предметов есть уникальный dbid (для каждого
предмета свой) и общий item_id (он же itemtype, берётся из itemname-e). Например Draconic Bow
имеет общий ID 7575, но у каждого игрока владеющего этим ДБ, лук будет иметь дополнительно
уникальный дбайди". Это подтверждено на данных: `[19]`=item_id/itemtype, `[26]`=dbid.

## Цель-NPC — РАСШИФРОВАНО (было открытым вопросом, решено в этой сессии)
Для событий, где целью действия является NPC (не другой персонаж) — например `928
FeeForWarehouse` (оплата хранения складу), `903`/`927` (снятие/добавление товара продавцу-нпс),
`105`/`111`/`113` (действия с питомцем) — поля `[24]`/`[25]` (target_name/login) ПУСТЫ, но в
одном из Num-полей закодировано составное число: **`npc_template_id + 1 000 000`**.

Подтверждено НАПРЯМУЮ через `game_lookup.build_lookup(cur, schema, server, 'npc')` (резолвинг из
`npcname-e.dat` дерева патчей сервера `c4x1`, файл появился в патчах между сессиями) на реальных
данных: `1007083 - 1000000 = 7083` → `"Pochi"` (точное совпадение с desktop-парсером), `1036096 -
1000000 = 36096` → `"Improved Baby Kookaburra"` (тоже точное совпадение). Проверено на нескольких
разных id из разных событий Saffeida — гипотеза подтвердилась без исключений.

**Позиция составного числа отличается по типу события**:
- `[16]` — для складских операций с NPC (`903` RemovFromInven, `927` AddedToWarehouse, `928`
  FeeForWarehouse, `929` RetrieveFromWarehouse — последний по аналогии, отдельно не проверен, в
  реальных данных Saffeida там просто не было NPC-цели в кадре).
- `[17]` — для событий, связанных с питомцем (`105` WithDrawPet, `111` GiveItemToPet, `113`
  PetUseItem) — там поле `[16]` занято ДРУГИМ числом (похоже на dbid самого питомца, не
  расшифровано отдельно, не критично для отображения цели).

Реализовано в `index.py`: `NPC_TARGET_OFFSET = 1_000_000`, `ACTION_NPC_TARGET_FIELD` (action_id →
индекс поля), логика в `_parse_log_line` — если `target` (из `[24]`) пусто, но
`ACTION_NPC_TARGET_FIELD` знает action_id, читаем составное число, вычитаем офсет, резолвим через
`refs['npc']` (тот же `game_lookup`, что и для `itemName`/`skillName`) и формируем `target =
f'Npc: {name}'` (формат СОВПАДАЕТ с desktop-парсером буквально), либо `f'Npc #{id}'`, если имя не
резолвится (npcname-e.dat не загружен/id не найден в справочнике — не считать багом). Фронтенд
менять не потребовалось — колонка "Цель" уже читает `event.target`, значение приходит готовым.

## ОТКРЫТЫЕ ВОПРОСЫ (не решены, для следующей сессии)
1. **Второе число в скобках у "Items count"** (`622 (742)` в исходном примере, `249 (250)` у
   Saffeida) — сырое поле `[21]` содержит только одно число (622 / 249). Второе число в скобках,
   видимо, вычисляется desktop-парсером (возможно остаток+модуль(дельты) = количество ДО операции)
   — не критично, можно посчитать на фронте как `itemsCountAfter + abs(itemCount)` если понадобится
   показать "было/стало", сейчас не реализовано.
2. **Позиция level для 403 CastSkill / 1112 PCKilledNPC** — предполагается `[17]` по аналогии с
   401 LearnSkill, но НЕ подтверждено отдельной сверкой (в прошлой сессии для 403/1112 сверяли
   только сам skill_id на `[16]`, не level).
3. **Остальные ~140+ уникальных action_id**, встреченные в логах — карта полей не построена,
   решено НЕ расшифровывать всё заранее вручную, а расширять по вопросам пользователя (см. план
   ниже). Для незнакомых action_id UI показывает просто `actionName=null` → фронт покажет `#id`.

## Источник справочников имён — ВАЖНОЕ УТОЧНЕНИЕ от пользователя (актуально!)
item/npc/skill резолвятся из **АКТУАЛЬНОГО дерева патчей конкретного сервера** (`itemname-e.dat`/
`npcname-e.dat`/`skillname-e.dat`, те же файлы, что раздел "Патчи" уже умеет расшифровывать через
DDF) — см. `backend/logs/game_lookup.py`. НЕ используется никакой статичный снимок для item/npc/
skill. `action_id` — ЕДИНСТВЕННЫЙ id, который берётся из статичного справочника (не игровой
ресурс, в дереве патчей его нет и быть не может).

**На момент последней проверки (сервер `c4x1`) `itemname-e.dat`/`npcname-e.dat`/`skillname-e.dat`
ЕЩЁ НЕ ЗАГРУЖЕНЫ в дерево патчей этого сервера** (проверено SQL: `SELECT path FROM patch_files
WHERE server='c4x1' AND path ILIKE '%itemname-e%'` → 0 строк) — поэтому `itemName`/`skillName` в
ответах API сейчас `null` даже для успешно найденного `itemId` (например `57`=Adena) — это
ОЖИДАЕМО, не баг. Резолвинг заработает автоматически, как только пользователь загрузит дерево
патчей C4 в раздел "Патчи" (game_lookup.py готов, просто нет исходных данных).

## ВАЖНАЯ ТЕХНИЧЕСКАЯ НАХОДКА: платформа НЕ деплоит не-.py файлы внутри папки backend-функции
Проверено на практике (временный debug-экшен): если положить данные в `backend/logs/reference/
action_ids.tsv` (читается через `open()` относительно `__file__`) — ЛОКАЛЬНО в проекте/в git файл
есть, но **в реальном облачном рантайме подпапка `reference/` физически отсутствует**
(`os.path.isdir()` → `False`, путь `/function/code/reference` не существует). Платформа деплоя
cloud-функций упаковывает в облако ТОЛЬКО `.py`-файлы (плюс `requirements.txt`/`tests.json`).
**Решение**: справочник `action_ids` встроен ПРЯМО В КОД как Python-словарь в отдельном модуле
`backend/logs/action_ids_data.py` (361 запись, сгенерирован одноразовым скриптом из
`action_ids.txt`, присланного пользователем). Папки `reference/` в проекте больше НЕТ (удалена).
**Правило на будущее для ЛЮБОЙ backend-функции этого проекта**: статичные данные — только (а)
литералом прямо в `.py`, либо (б) в БД/S3, НИКОГДА не полагаться на чтение соседних не-`.py`
файлов через `open()` — не будет работать в облаке (хотя в локальной песочнице может ошибочно
"работать" — это ловушка).

## ВАЖНАЯ ТЕХНИЧЕСКАЯ НАХОДКА: SFTP-чтение больших файлов требует prefetch()
`sftp.open(path, 'rb').read()` БЕЗ `.prefetch(size)` перед `.read()` тянет файл СИНХРОННЫМИ мелкими
запросами один за другим — на реальных файлах логов (несколько МБ, обычный размер при нарезке
каждые 30 минут) это упиралось в таймаут облачной функции (5 сек, `JobExecutionTimeoutExceeded`).
**Решение**: `f.prefetch(st.st_size)` перед `f.read()` — конвейерные запросы, файл ~2.6МБ читается
за ~2-3 сек вместо таймаута. Проверено на реальном сервере `c4x1`. НЕ УБИРАТЬ этот вызов.

## Копирование DDF-инфраструктуры (backend-функции физически изолированы друг от друга)
`backend/logs/index.py` НЕ может импортировать модули из `backend/patches/` — платформа грузит
каждую cloud-функцию в свой Python-namespace с `sys.path`, содержащим ТОЛЬКО папку этой функции.
Поэтому в `backend/logs/` физически СКОПИРОВАНЫ 4 файла из `backend/patches/`: `ddf_parser.py`,
`ddf_registry.py`, `ddf_registry_c4.py`, `l2encdec.py`. Если в оригиналах появятся исправления
формата DDF/шифрования — копии НЕ обновятся автоматически, синхронизировать вручную.

## Реальная структура каталогов на VPS — РЕШЕНО
Под `servers.logs_dir` (например `/var/www/era/test_updater/log` для `c4x1`) лежат три подпапки
`server/`, `npc/`, `cashed/` (с ОПЕЧАТКОЙ в имени папки — подтверждено скриншотом пользователя).
Сами файлы внутри называются с правильным словом `...-cached-...log`. Несовпадение зафиксировано
в коде через `LOG_TYPE_DIR = {'cached': 'cashed', 'server': 'server', 'npc': 'npc'}` в
`backend/logs/index.py` — `log_type` (API/regex имени файла) всегда `'cached'`, а при построении
SFTP-пути подставляется `LOG_TYPE_DIR[log_type]` = `cashed`. Если пользователь переименует папку
на сервере в `cached` без опечатки — поправить `LOG_TYPE_DIR['cached'] = 'cached'` (одна строка).

## Технический debug-флаг `debugRaw=1` (для внутреннего использования, не в UI)
`action=get_log` поддерживает необязательный параметр `debugRaw=1` — каждое событие в ответе
дополнительно содержит поле `raw` (все 27 сырых CSV-полей). НЕ используется фронтендом. Оставлен
специально для будущей отладки новых action_id без похода на VPS вручную, пример:
`?action=get_log&server=X&type=cached&file=Y&player=ник&actionQuery=ID&debugRaw=1`. НЕ УБИРАТЬ.

## Архитектура (реализовано)
- `backend/logs/index.py` — handler, action-роутинг (`list_files`, `get_log`), право `logs_view`
  (отдельное от `patch_edit`, `db_migrations/V0075__add_logs_dir_and_logs_view_permission.sql`),
  SFTP через `paramiko` (креды в `service_keys`: `LOGS_SFTP_HOST/PORT/USER/PASSWORD`, единый хост
  на все сервера), путь конкретного сервера — колонка `servers.logs_dir`.
- `backend/logs/game_lookup.py` — резолвинг item/npc/skill из дерева патчей (S3 + DDF).
- `backend/logs/action_ids_data.py` — статичный справочник action_id → имя, встроен ПРЯМО В КОД.
- `backend/logs/ddf_parser.py`/`ddf_registry.py`/`ddf_registry_c4.py`/`l2encdec.py` — копии из
  `backend/patches/` (см. выше).
- `backend/logs/requirements.txt` — `psycopg2-binary`, `paramiko`, `boto3`.
- `backend/logs/tests.json` — 3 теста (OPTIONS, 401 без токена на оба действия).
- Фронтенд: `src/pages/index/Logs.tsx` — выбор сервера/типа лога/файла, фильтры (игрок/предмет/
  действие), таблица (Время/Действие/Игрок/Цель/Предмет/Кол-во/DB item id), пагинация; `LOGS_URL`
  в `src/pages/index/sharedHelpers.ts`; `ViewId`/`NAV_ITEMS`/монтирование — как у "Патчей".

## Тестовый доступ для проверки (dev-режим редактора)
`backend/dev-login` выдаёт токен владельца проекта (`OWNER_USER_ID`, роль admin, есть `logs_view`).
Сервер `c4x1` уже имеет заполненные `logs_dir` и `LOGS_SFTP_*` service_keys — можно проверять
`action=list_files`/`get_log` прямо curl'ом без похода в браузер. `hfx3old`/`hfnew` — `logs_dir`
пока `NULL`, для них `get_log`/`list_files` вернут `logs_dir_not_configured`.

# Индексатор логов — быстрый поиск по неделям истории

## Зачем это нужно

Раньше раздел «Логи» кабинета при каждом поиске заново скачивал и разбирал файлы логов
по SFTP с игрового сервера. Это работает для пары часов истории, но неделя логов — это
сотни файлов и десятки-сотни мегабайт текста на КАЖДЫЙ поиск, что либо очень медленно, либо
вообще не укладывается в разумное время ответа.

Решение: отдельный скрипт (`indexer.py`) запускается **прямо на хостинге, где лежат файлы
логов** (без сети — читает файлы напрямую с диска), один раз разбирает каждую строку и
складывает результат в свою PostgreSQL-базу. Дальше кабинет читает из этой базы — поиск по
любому диапазону дат (неделя, месяц — не важно) выполняется через индексы, то есть мгновенно.

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│   Хостинг логов (VPS игры)  │        │   Хостинг проекта ERA         │
│                              │        │                                │
│  файлы *.log на диске        │        │  основной backend (server.py) │
│         │                    │        │         │                      │
│         ▼                    │        │         ▼                      │
│  indexer.py (таймер 1 раз/мин)│        │  читает logs_events напрямую  │
│         │                    │        │  (быстрый SQL-запрос)         │
│         ▼                    │        │                                │
│  PostgreSQL "era_logs" ──────┼────────┼──────────────►                 │
│  (logs_events, logs_indexed_files)     │                                │
└─────────────────────────────┘        └──────────────────────────────┘
```

Если хостинг логов и хостинг проекта — один и тот же сервер, всё ещё проще: обе базы (основная
`era_db` и `era_logs`) живут на одном Postgres, backend подключается к `era_logs` напрямую по
`localhost`. Если это разные серверы — база логов должна быть доступна backend'у по сети (открыт
порт 5432 с ограничением по IP, либо туннель).

## Что здесь лежит

| Файл | Назначение |
|---|---|
| `schema.sql` | SQL создания таблиц `logs_events` (разобранные события) и `logs_indexed_files` (что уже прочитано) |
| `indexer.py` | Сам скрипт индексации — точка входа |
| `game_lookup.py`, `ddf_parser.py`, `ddf_registry.py`, `ddf_registry_c4.py`, `l2encdec.py` | Копии модулей резолва имён предметов/нпс/скиллов из дерева патчей (те же, что в `backend/logs/`) — нужны только если хотите видеть человекочитаемые имена, а не числовые id |
| `action_ids_data.py` | Справочник `action_id → название действия` (та же копия, что в `backend/logs/`) |
| `requirements.txt` | Python-зависимости индексатора |
| `.env.example` | Шаблон настроек — скопируйте в `.env` и заполните |
| `era-logs-indexer.service` / `.timer` | systemd-юниты для регулярного автозапуска |

## Установка

### 1. Создайте базу логов

Если Postgres уже стоит на этом сервере (например тот же, что для основной базы проекта):

```bash
sudo -u postgres psql -c "CREATE USER era_logs_user WITH PASSWORD 'ВАШ_ПАРОЛЬ';"
sudo -u postgres psql -c "CREATE DATABASE era_logs OWNER era_logs_user;"
psql "postgresql://era_logs_user:ВАШ_ПАРОЛЬ@localhost:5432/era_logs" -f schema.sql
```

### 2. Разложите файлы индексатора

```bash
sudo mkdir -p /var/www/era-logs-indexer
sudo chown -R $USER:$USER /var/www/era-logs-indexer
# скопируйте ВСЕ файлы этой папки (logs-indexer/) в /var/www/era-logs-indexer/
```

### 3. Python-окружение

```bash
cd /var/www/era-logs-indexer
python3 -m venv venv
venv/bin/pip install -r requirements.txt
```

### 4. Настройте `.env`

```bash
cp .env.example .env
nano .env   # заполните LOGS_DB_URL, LOGS_ROOT, LOGS_SERVERS (см. комментарии в файле)
```

**`LOGS_ROOT`** — важно указать так, чтобы `LOGS_ROOT/<server_id>/cashed/*.log` (и `server/`,
`npc/` рядом) вело на реальные файлы. Проверьте командой:
```bash
ls $LOGS_ROOT/<ваш_server_id>/cashed/ | head
```
Если структура на вашем хостинге отличается — либо переименуйте/примонтируйте папки под этот
шаблон, либо сообщите мне (Юре), и я адаптирую `indexer.py` под вашу структуру.

### 5. Проверьте разовый запуск

```bash
cd /var/www/era-logs-indexer
set -a; source .env; set +a
venv/bin/python3 indexer.py
```

Ожидаемый вывод — что-то вроде:
```
[indexer] c4x1/cached/2026-08-08-...-in0.log: +48127 новых строк
[indexer] Готово. Всего новых строк за этот прогон: 48127
```

Если видите `WARN: директория сервера не найдена` — проверьте `LOGS_ROOT`/`LOGS_SERVERS`.

Первый запуск на большом объёме уже накопленных логов может занять несколько минут — это
нормально, дальше (когда всё уже проиндексировано) каждый запуск обрабатывает только новые
строки и выполняется за секунды.

### 6. Настройте автозапуск по таймеру

Отредактируйте пути в `era-logs-indexer.service`, если разложили файлы не в
`/var/www/era-logs-indexer` — затем:

```bash
sudo cp era-logs-indexer.service /etc/systemd/system/
sudo cp era-logs-indexer.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now era-logs-indexer.timer
```

Проверить, что таймер зарегистрирован и работает:
```bash
systemctl list-timers era-logs-indexer.timer
journalctl -u era-logs-indexer.service -n 50 --no-pager
```

### 7. Подключите backend проекта к базе логов

В кабинете (раздел **Служебные ключи**) заполните появившиеся там поля подключения к базе
логов (`LOGS_DB_URL` и, если нужен резолв имён — `LOGS_DB_ENABLED`). После этого backend
проекта САМ определит, что база логов настроена, и начнёт читать данные из неё вместо
медленного SFTP-обхода — никаких дополнительных действий на фронтенде не требуется.

Если поля оставить пустыми — раздел «Логи» продолжит работать по-старому (через SFTP), просто
без ускорения на широких диапазонах.

## Хранение истории

По умолчанию база хранит **7 дней** — старые события удаляются автоматически при каждом
запуске индексатора (см. `RETENTION_DAYS` в `.env`). Чтобы хранить дольше — увеличьте значение
и перезапустите таймер (перезапуск не обязателен, подхватится на следующем плановом запуске).

## Что если структура файлов на VPS логов не совпадает с ожиданиями скрипта

`indexer.py` ожидает: `LOGS_ROOT/<server_id>/cashed/*.log`, `LOGS_ROOT/<server_id>/server/*.log`,
`LOGS_ROOT/<server_id>/npc/*.log`, имена файлов вида
`{ГГГГ-ММ-ДД}-{HHMM}-{NN}-{cached|server|npc}-in{0|1}.log`. Это та же структура, что уже
предполагает раздел «Логи» в его SFTP-режиме (см. `backend/logs/RESEARCH_NOTES.md`). Если у вас
реальная структура отличается — самый простой вариант: сделать симлинки на нужные пути
(`ln -s /реальный/путь /var/www/l2logs/c4x1`), не трогая сам скрипт.
